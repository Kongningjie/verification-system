# Review 规范

## 1. Review 目标

Review 不只是检查代码风格，必须验证：

- 是否忠实实现冻结方案和当前阶段。
- 是否产生错误业务结论或虚假证据。
- 是否存在数据泄露、文件越界或密钥泄露。
- 状态、数据库和文件系统是否保持一致。
- 错误能否被正确观察、重试和恢复。
- 测试是否证明了行为，而非只覆盖代码行。

## 2. Review 前置条件

提交 Review 前，作者必须提供：

- 变更目的与当前阶段。
- 改动文件清单。
- 关键设计选择及与冻结方案的对应关系。
- 数据库迁移说明。
- 实际运行的测试命令和结果。
- 未执行的测试及原因。
- 已知限制和风险。
- 冻结方案哈希校验结果。

缺少上述信息时可以拒绝进入正式 Review。

## 3. 严重级别

### P0：立即停止

包括但不限于：

- API Key、用户材料或敏感数据泄露。
- 路径穿越、任意文件读取/覆盖/删除。
- 修改、覆盖或绕过冻结方案。
- 伪造证据、无证据输出 PASS/FAIL。
- 破坏或修改用户原始上传材料。
- 通过强制推送或历史改写造成仓库风险。

处理：停止合并和后续开发，优先修复并执行安全回归。

### P1：阶段阻断

包括但不限于：

- 状态机或结论语义错误。
- 技术错误被包装成 `NEEDS_REVIEW`。
- 确定性规则被 LLM 覆盖。
- 来源冲突时擅自选择权威依据。
- 清单确认后仍可静默修改。
- 系统原始结论被人工结论覆盖。
- 数据库和文件系统出现不可检测的不一致。
- 核心路径没有测试或测试无法复现。

处理：本阶段不得完成，修复后重新 Review。

### P2：应在本阶段处理

包括：

- 错误处理不完整。
- 边界条件遗漏。
- 性能或资源释放问题。
- 模块耦合、重复代码和难以测试的设计。
- 用户错误提示不清晰。
- 非关键接口或报告字段不一致。

处理：本阶段修复；确需延期必须记录并经用户接受。

### P3：优化建议

包括命名、局部可读性、非必要优化和体验微调。不得借 P3 扩大产品范围。

## 4. Review 顺序

按风险从高到低检查：

1. 冻结方案与阶段范围。
2. 安全、密钥和文件边界。
3. 业务状态、结论和证据语义。
4. 数据库一致性和迁移。
5. 错误、重试、取消和恢复。
6. 测试有效性。
7. 架构分层和可维护性。
8. 性能、可观测性和前端体验。
9. 代码风格。

不要因格式问题分散对高风险业务问题的注意。

## 5. 通用 Review 清单

### 5.1 范围与契约

- 变更是否只属于当前获准阶段。
- 是否新增冻结方案未允许的格式、服务或基础设施。
- API、Pydantic、数据库和前端枚举是否一致。
- 是否存在魔法字符串绕过集中契约。
- 是否改变了已有接口而未更新调用方和测试。

### 5.2 结论与证据

- 每个 PASS/FAIL 是否都有有效证据 ID。
- 未定位证据时是否明确返回缺失原因。
- 来源冲突是否转 `SOURCE_CONFLICT`。
- 模型是否只能引用候选证据。
- 二次独立判断是否看不到第一次结论。
- `ERROR`、`NEEDS_REVIEW`、`FAILED`、`COMPLETED_WITH_ERRORS` 是否正确区分。

### 5.3 数据与事务

- 数据库写入和文件落盘的顺序是否可恢复。
- 失败、取消和重试是否产生重复记录或孤立文件。
- 删除是否限制在明确任务目录。
- 迁移是否可升级和回退。
- 并发更新是否使用版本或事务保护。

### 5.4 安全

- 所有文件路径是否经过根目录校验。
- OOXML/XML/图片解析是否有资源限制。
- 日志、异常、报告和 API 是否脱敏。
- 前端是否安全展示不可信文档内容。
- Agent 是否无工具且不采纳文档内指令。
- 下载和删除接口是否只使用业务 ID。

### 5.5 并发与可靠性

- 是否仍保持任务间串行、任务内并行。
- 信号量是否对整个模型运行层生效。
- 重试是否只针对临时错误并有上限。
- 取消、超时和重启中断能否收敛到稳定状态。
- SSE 断线后是否可从数据库恢复当前状态。

### 5.6 前端

- 页面是否完整处理加载、空数据、错误和重试。
- 是否把业务判断放进组件。
- 是否存在无类型 API 数据或无理由 `any`。
- 高风险操作是否有明确确认和反馈。
- 页面、数据库和报告显示的最终结论是否一致。

## 6. Review 意见格式

每条问题使用：

```text
[P1] 标题
位置：文件与行号
事实：当前代码实际做了什么
风险：为什么违反冻结方案或会造成错误
建议：最小可行修复方向
验证：修复后应运行的测试
```

要求：

- 聚焦可验证事实，不使用模糊评价。
- 行号范围保持最小。
- 一个问题只描述一个根因。
- 不要求与任务无关的重构。
- 没有问题时明确说明“未发现阻断问题”，但仍列出残余风险和未执行测试。

## 7. Review 完成条件

- 所有 P0/P1 已修复并重新验证。
- P2 已修复或有明确、获接受的延期记录。
- 新增修复有对应回归测试。
- 全量质量命令通过。
- 冻结方案哈希不变。
- Review 结论、测试结果和残余风险已报告给用户。
- 未获用户允许，不得进入下一阶段。
