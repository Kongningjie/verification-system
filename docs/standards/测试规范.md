# 测试规范

## 1. 测试目标

测试必须证明系统在正常、异常和恶意输入下均保持冻结方案定义的行为，尤其保护：

- 核对项不遗漏。
- 结论与错误语义正确。
- 证据真实可追溯。
- 用户文件和密钥安全。
- 状态、数据库和文件系统一致。
- 模型不稳定不会直接造成相反结论。

测试不是为了追求单一覆盖率数字，关键业务分支和风险边界必须有明确断言。

## 2. 测试层级

### 2.1 单元测试

范围：纯函数、Schema、规则、解析片段、状态转换、错误映射、聚合和指标计算。

要求：

- 快速、确定、无网络、无真实 API Key。
- 每个测试只验证一个主要行为。
- 使用最小夹具，失败信息能指向具体规则。
- 时间、UUID、随机数和模型输出应可注入或固定。

### 2.2 集成测试

范围：API + Service + Repository + SQLite + 临时文件目录、完整解析器、Fake Agent Workflow。

要求：

- 每个测试使用独立临时数据库和目录。
- 测试结束不残留任务文件、数据库或后台任务。
- 验证数据库记录与磁盘状态，而不只验证 HTTP 状态码。
- 覆盖失败、取消、重试和后端重启恢复。

### 2.3 模型契约测试

范围：真实 `openai-agents` 与配置模型的结构化输出、图片输入、并发和错误映射。

要求：

- 默认与普通测试分离，使用明确标记，例如 `model_contract`。
- 仅在本地存在真实 API Key 时执行。
- 不打印密钥、完整提示词、完整文档或模型原始响应。
- 固定低成本专用夹具，并记录模型、提示词版本、耗时和 Token。
- 未运行必须报告，不能以 Fake Agent 通过代替真实契约测试。

### 2.4 端到端测试

范围：从上传材料到清单确认、核对、人工复核和报告下载。

要求：

- 关键主流程使用 Fake Agent 保证可重复。
- 阶段 5 使用真实模型运行代表性任务包。
- 同时验证 UI、API、数据库、文件和导出报告的一致性。

### 2.5 安全与稳健性测试

覆盖：

- 路径穿越和任意路径下载。
- Zip Slip、压缩炸弹、XML 外部实体和超大 XML。
- 损坏 DOCX/PDF/图片、超大图片和扫描型 PDF。
- Prompt Injection、文档伪系统指令和未知 evidence ID。
- 日志、数据库、报告和前端响应的密钥扫描。
- 网络超时、限流、认证失败、磁盘写入失败和进程中断。

## 3. 测试目录与命名

后端建议结构：

```text
backend/tests/
├── unit/
├── integration/
├── contract/
├── security/
├── fixtures/
└── conftest.py
```

命名规则：

- 文件：`test_<模块>.py`。
- 测试：`test_<条件>_<预期行为>`。
- 夹具名表达业务含义，例如 `docx_comment_in_table`，不使用 `sample1`。
- 回归测试应在名称或注释中说明对应缺陷。

前端测试按组件、页面和端到端分层；不得只依赖快照测试验证业务行为。

## 4. 夹具规范

- 夹具必须是最小可复现材料，避免依赖个人目录。
- 可程序生成的恶意或边界文件应通过测试工厂生成。
- 二进制夹具必须记录用途、来源和预期解析结果。
- 不提交真实 API Key、生产数据或未经脱敏的内部材料。
- DOCX 夹具至少覆盖正文、表格、跨 Run 批注、损坏范围和邻近图片。
- PDF 夹具至少覆盖文本型、扫描型、损坏文件和多页坐标。
- 图片夹具至少覆盖 EXIF 方向、超大像素和损坏文件。
- 模型响应夹具必须符合或故意违反明确的 Pydantic Schema。

## 5. Fake Agent 规范

- Fake Agent 与真实 Agent 实现相同接口。
- 输出根据显式测试输入或预置场景生成，不根据文件名硬编码业务答案。
- 可模拟成功、Schema 错误、超时、限流、认证失败和结果不一致。
- 可记录收到的输入，用于断言二次判断没有收到第一次结论。
- Fake Agent 只验证 Workflow，不代表真实模型质量。

## 6. 数据库和迁移测试

每个新迁移至少验证：

1. 从上一个版本升级成功。
2. 模型与数据库结构一致。
3. 新数据约束实际生效。
4. `downgrade()` 能回到前一版本。
5. 从空库连续升级到最新版本成功。

禁止用现有开发数据库替代迁移测试。

## 7. 状态和结论测试矩阵

至少覆盖：

| 场景 | 核对项结论 | 任务状态 |
|---|---|---|
| 全部成功 | PASS/FAIL/NEEDS_REVIEW/NOT_APPLICABLE | `COMPLETED` |
| 存在技术失败项 | 至少一个 `ERROR` | `COMPLETED_WITH_ERRORS` |
| 输入或解析阻断 | 未形成有效核对结果 | `FAILED` |
| 用户取消 | 保留已完成记录 | `CANCELLED` |
| 进程重启中断 | 未完成工作不伪装成功 | `INTERRUPTED` |
| 来源冲突 | `NEEDS_REVIEW/SOURCE_CONFLICT` | 非技术错误 |
| 双重判断不一致 | `NEEDS_REVIEW/MODEL_DISAGREEMENT` | 非技术错误 |

还必须断言：技术错误不能变成 `NEEDS_REVIEW`，人工结论不能覆盖系统原始结论。

## 8. 前端测试要求

- TypeScript 类型检查必须通过。
- 生产构建必须通过。
- API 错误、加载、空数据、取消和重试状态必须测试。
- 任务列表、上传、清单确认、进度、结果详情、人工复核和报告下载按阶段覆盖。
- `ERROR`、`NEEDS_REVIEW`、`FAIL` 的视觉与文案语义应有断言。
- 不可信原文按纯文本渲染，使用恶意 HTML 夹具验证不会执行。
- SSE 断线后应先查询当前任务状态再恢复订阅。

## 9. 覆盖率规则

- 新增核心业务代码必须有对应测试，不接受“后续补测试”。
- 状态转换、结论聚合、证据白名单、路径安全和人工改判规则要求分支全覆盖。
- 普通模块总体覆盖率建议不低于 80%，但高覆盖率不能替代关键断言。
- 生成代码、简单迁移模板和纯类型声明可按理由排除。
- 覆盖率下降必须解释并经 Review 接受。

## 10. 标记与执行

建议 pytest 标记：

- `unit`
- `integration`
- `model_contract`
- `security`
- `slow`

普通提交必须执行无网络测试；阶段完成时执行当前阶段和此前阶段全部测试。真实模型和慢速评估单独运行并明确报告。

基础命令：

```powershell
.\.venv\Scripts\python.exe -m ruff check backend
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m alembic upgrade head
Set-Location frontend
npm run type-check
npm run build
```

在支持对应测试脚本后，还应执行前端单元和端到端测试。

## 11. 失败处理

- 测试失败时先保留完整失败事实，再定位根因。
- 不得删除失败测试、放宽断言或添加无条件跳过来通过门禁。
- 修复缺陷必须新增或强化回归测试。
- 不稳定测试必须修复其随机性、时间或资源依赖；不得无限重跑掩盖。
- 依赖真实服务的失败需区分产品缺陷、契约变化和外部暂时故障。

## 12. 测试报告

每阶段报告至少包含：

- 测试日期和环境。
- Git 提交或工作区状态。
- 执行命令。
- 通过、失败、跳过数量。
- 真实模型测试是否执行。
- 失败与修复摘要。
- 未覆盖风险。
- 冻结方案哈希。

只有实际执行结果可以写为“通过”；计划执行或推测通过不得写成测试结果。
