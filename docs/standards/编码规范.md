# 编码规范

## 1. 基本原则

- 业务正确性、证据可追溯性和数据安全优先于开发速度。
- 规则逻辑、模型逻辑、基础设施和界面逻辑必须分层。
- 函数和模块只承担单一职责，避免隐式全局状态。
- 所有失败必须显式表达；不得使用空结果或默认通过掩盖异常。
- 不为尚未获准的后续阶段预先实现功能。
- 不修改用户原始上传文件。
- 不修改冻结方案，除非用户明确授权。

## 2. Python 规范

### 2.1 版本与风格

- 支持 Python 3.12 和 3.13。
- 使用 Ruff 作为统一静态检查工具。
- 行宽上限遵循 `pyproject.toml`，当前为 100。
- 所有公共函数、方法和属性必须有完整类型标注。
- 使用 Python 3.12+ 语法：`str | None`、内置泛型和 `StrEnum`。
- 时间统一使用带时区 UTC，禁止使用无时区 `datetime.now()`。
- 路径使用 `pathlib.Path`，不得手工拼接路径分隔符。

### 2.2 命名

- 模块、函数、变量：`snake_case`。
- 类、Pydantic 模型、异常：`PascalCase`。
- 常量：`UPPER_SNAKE_CASE`。
- 枚举成员使用冻结方案定义的大写稳定值。
- 数据库表和字段使用 `snake_case`。
- ID 名称必须表达对象，例如 `task_id`、`evidence_id`，不得使用含糊的 `id_1`。

### 2.3 函数和异常

- 一个函数应有明确输入、输出和错误边界。
- 业务异常使用项目自定义异常类型和稳定错误码。
- 禁止裸 `except:`，禁止捕获异常后不处理。
- 只有在边界层转换异常：解析器转解析错误、模型层转模型错误、API 层转统一响应。
- 日志记录异常时不得包含 API Key、完整文档、图片 Base64 或完整模型提示词。
- 重试只应用于明确的临时错误，认证错误、参数错误和确定性内容错误不得重试。

### 2.4 Pydantic 契约

- API、Agent 输出、配置和跨模块数据均使用显式 Pydantic 模型。
- 输入模型默认拒绝未声明字段，只有冻结方案允许的扩展结构可放宽。
- 字段必须有语义明确的类型、枚举和约束，不使用无边界 `dict[str, object]` 代替稳定契约。
- 模型输出验证失败是技术错误，不得转为业务 `NEEDS_REVIEW`。
- 所有外部 JSON 输出必须包含 `schema_version`。

## 3. 后端分层

### 3.1 目录职责

- `api/`：HTTP 路由、参数转换和响应；不得实现核心业务。
- `schemas/`：Pydantic 输入输出契约。
- `models/`：SQLAlchemy 持久化模型。
- `repositories/`：数据库读写；不得调用模型或处理 HTTP。
- `parsers/`：DOCX、PDF、图片和项目 JSON 解析。
- `rules/`：通用规则定义和确定性执行器。
- `evidence/`：候选证据构建、排序和证据 ID 管理。
- `agents/`：OpenAI Agents SDK 封装、提示词和结构化输出。
- `workflow/`：固定阶段编排和状态转换。
- `services/`：应用级用例协调。
- `reports/`：Excel 和 JSON 报告。
- `core/`：配置、日志、错误和运行时基础能力。

禁止跨层直接访问，例如路由直接操作磁盘、Agent 直接访问数据库、解析器更新任务状态。

### 3.2 API

- 统一前缀 `/api/v1`。
- 路由函数保持简短，将业务委托给 Service。
- 错误响应统一包含 `code`、`message`、`details`、`request_id`。
- 不向客户端暴露堆栈、绝对路径、密钥和完整内部异常。
- 所有状态变更必须校验当前任务状态。
- 清单编辑等并发更新必须使用版本号或等价乐观锁。
- 文件下载只接受业务 ID，不接受用户传入磁盘路径。

### 3.3 Workflow 与状态

- 状态转换集中维护，禁止在任意模块直接写字符串状态。
- 每次状态更新、阶段更新和关键操作应在同一事务边界内保持一致。
- 单项技术错误使用 `ERROR`，不得误标为业务不确定。
- 任务级阻断使用 `FAILED`；部分核对项技术失败使用 `COMPLETED_WITH_ERRORS`。
- 后端重启后活动任务必须转为 `INTERRUPTED`。

## 4. 数据库规范

- 所有表使用 Alembic 迁移创建，不允许运行时 `create_all` 替代正式迁移。
- 迁移必须提供 `upgrade()` 和合理的 `downgrade()`。
- 迁移一经推送不得原地修改；新增迁移修正。
- 外键、唯一约束和高频查询字段应显式定义。
- 大文件、图片和文档内容不以 BLOB 存入 SQLite。
- JSON 字段必须有对应 Pydantic 契约，不得成为无约束数据垃圾桶。
- 删除任务必须考虑数据库与文件系统的一致性和失败恢复。
- API Key 永不进入数据库。

## 5. 文件与解析安全

- 上传文件视为不可信输入。
- 磁盘文件名使用系统生成 UUID；原始文件名只作为元数据。
- 所有解析后路径必须验证仍位于对应 `task_id` 目录内。
- 同时校验扩展名、MIME 和文件签名。
- OOXML 解压必须防 Zip Slip、压缩炸弹和过大解压总量。
- XML 解析禁用外部实体、DTD 和网络访问。
- 图片限制像素、尺寸和解码资源。
- 不支持的结构产生显式警告或错误，不得静默忽略。
- DOCX Locator 使用逻辑位置，不伪造页码。

## 6. Agents SDK 规范

- 使用 `openai-agents` 作为应用内模型运行层。
- Agent 无工具、无 Handoff、无 Session、无 MCP、无网络搜索和文件系统访问。
- 固定 Workflow 由 Python 代码控制，模型不得决定业务阶段。
- 所有 Agent 输出使用 Pydantic 结构化输出。
- 模型只能引用系统提供的 `evidence_id`。
- 上传文档必须被标记为不可信数据，不能成为系统指令。
- 默认关闭远程 tracing；未经评审不得开启敏感输入输出采集。
- API Key 只从 `.env` 读取，不进入日志、数据库、报告或前端。
- 测试必须提供 Fake Agent，真实 API 测试不得成为普通单元测试的前置条件。
- 模型、规则集和提示词均需记录稳定版本。

## 7. 前端规范

### 7.1 TypeScript 与 Vue

- 使用 Vue 3 Composition API 和 `<script setup lang="ts">`。
- 开启严格 TypeScript，业务代码不得使用无理由 `any`。
- API 类型集中定义，页面不自行猜测后端结构。
- 页面只负责展示与交互，不实现结论聚合和证据判断。
- 全局状态只放跨页面、需要持久存在的数据；局部状态留在组件。
- 可复用交互拆成组件或 composable，避免超大页面组件。

### 7.2 UI 与安全

- 每个异步操作必须有加载、成功、空数据和错误状态。
- `ERROR`、`NEEDS_REVIEW` 和 `FAIL` 必须视觉区分。
- 用户上传文本必须按纯文本展示，禁止未经清洗的 `v-html`。
- 删除、确认清单和人工改判等操作需要明确确认反馈。
- 不在浏览器保存 API Key。
- 大列表必须分页或虚拟化；不得一次加载全部图片原图。

## 8. 日志与配置

- 配置统一由 `pydantic-settings` 加载。
- `.env.example` 只包含示例或空值，不得提交真实密钥。
- 日志采用结构化字段，至少包含 `request_id`、`task_id`、`stage`、`operation` 和 `error_code`。
- 禁止用 `print` 代替应用日志。
- 开发日志也必须遵守脱敏规则。
- 环境差异通过配置解决，不在代码中写个人绝对路径。

## 9. 注释与文档

- 注释解释“为什么”和业务约束，不重复代码表面含义。
- 对安全边界、状态转换和不直观算法写简短说明。
- 公共 API、配置项、启动命令和限制同步更新非冻结文档。
- TODO 必须说明原因和后续条件，禁止无上下文 TODO。
- 不把实现细节反向写入或修改冻结方案。

## 10. 提交前检查

```powershell
.\.venv\Scripts\python.exe -m ruff check backend
.\.venv\Scripts\python.exe -m pytest
Set-Location frontend
npm run type-check
npm run build
```

提交前还必须确认：

- `git diff --check` 通过。
- `git status` 中没有 `.env`、运行数据库、上传材料或构建产物。
- 冻结方案哈希未变化。
- 本次变更只属于当前获准阶段。
