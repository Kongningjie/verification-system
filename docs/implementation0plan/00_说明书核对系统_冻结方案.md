# 说明书核对系统一期 MVP 冻结方案

> 状态：**FROZEN**  
> 版本：1.0  
> 冻结日期：2026-09-20  
> 用途：作为后续 AI Coding 的唯一实施基线。若本文与早期《说明书核对_技术方案》冲突，以本文为准。  
> 本阶段只生成方案，不包含代码实现。

## 1. 文档约束

本文中的关键词含义如下：

- **必须**：MVP 验收所必需，不得由编码执行者自行删减或替换。
- **应当**：默认实现；只有发现明确技术阻断时才允许调整，并需记录原因。
- **可以**：可选实现，不影响 MVP 验收。
- 未经新的方案评审，不得扩大文件格式、部署、用户系统、OCR、模板库或自动学习范围。

## 2. 目标与成功定义

### 2.1 产品目标

实现一个可在 Windows 本地运行的单用户 Web 应用，完成以下闭环：

1. 上传 DOCX 说明书、DOCX 模板、项目 JSON 和核对依据材料。
2. 从模板 Word 批注中生成模板特有核对项，并与内置通用规则合并。
3. 由用户预览、修改并确认核对清单。
4. 使用确定性规则、文本模型和视觉模型执行核对。
5. 展示结论、原因和可追溯证据。
6. 支持人工复核并完整保留系统原始结论。
7. 导出 Excel 和 JSON 报告。

### 2.2 MVP 性质

一期是**固定业务边界内可用的验证型 MVP**，目标是验证核对流程、准确性和证据链，不是生产级通用平台。

### 2.3 验收指标

必须准备至少 5 组代表性任务包，每组包含输入材料、人工确认的核对项清单和正确结论。

| 指标 | 验收门槛 |
|---|---:|
| 关键核对项召回率 | 100% |
| 全部核对项召回率 | ≥95% |
| 可判定核对项结论准确率 | ≥90% |
| 结论证据可追溯率 | 100% |
| 虚构证据次数 | 0 |
| 单任务端到端耗时 | ≤5 分钟（不含用户确认等待） |
| 通用规则重复运行一致性 | 100% |

同一输入连续运行三次时，LLM 结论不得在 `PASS` 与 `FAIL` 之间直接漂移；独立复核不一致时必须转为 `NEEDS_REVIEW`。

## 3. MVP 范围

### 3.1 支持范围

| 材料 | 格式 | 约束 |
|---|---|---|
| 待核对说明书 | DOCX | 必须可正常读取，不承诺页码 |
| 说明书模板 | DOCX | 特殊要求必须写在 Word 批注中 |
| 项目信息 | JSON | 必须符合本文约定 Schema |
| 文字依据 | PDF | 只支持可提取文字的 PDF |
| 图片依据 | PNG、JPG、JPEG | 使用视觉模型核对 |

### 3.2 明确不做

- DOC、TXT、Markdown 作为业务输入。
- 扫描型 PDF OCR、手写文字识别。
- 任意模板正文自动推断全部要求。
- Word/WPS/LibreOffice 自动化及 DOCX 精确页码计算。
- 向量数据库、Embedding、文件搜索服务。
- MinIO、S3 或其他对象存储。
- Celery、Redis、PostgreSQL。
- Docker、生产部署、Kubernetes、多机或高可用。
- 登录、注册、用户、角色和权限系统。
- 多 Agent 协作、Handoff、动态工具选择、Agent 会话记忆。
- 自动修改原说明书或模板。
- 根据人工复核自动学习、自动修改规则或提示词。
- 跨任务模板库和已上传文件复用。

## 4. 冻结技术栈

### 4.1 前端

- Vue 3 + TypeScript + Vite。
- Vue Router。
- Pinia。
- Element Plus。
- 原生 `EventSource` 接收 SSE。
- 前端只负责交互和展示，不承载业务判定逻辑。

### 4.2 后端

- Python 3.12。
- FastAPI + Uvicorn。
- Pydantic 2 + pydantic-settings。
- SQLAlchemy 2 + Alembic。
- SQLite。
- OOXML 解析：`zipfile` + `lxml`；`python-docx` 只用于其擅长的正文辅助读取，不作为批注映射的唯一实现。
- PDF：PyMuPDF。
- 图片：Pillow。
- Excel：openpyxl。
- 重试：tenacity 或等价的集中式重试封装。
- 模型运行：OpenAI Agents SDK for Python。

Agents SDK 只用于定义无工具 Agent、通过 Runner 执行模型请求、接收 Pydantic 结构化输出和统计调用信息。业务编排由 Python 固定 Workflow 完成。官方能力基线参考 [Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk)、[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 与 [Images and vision](https://developers.openai.com/api/docs/guides/images-vision)。

### 4.3 模型配置

`.env` 至少包含：

| 配置 | 说明 |
|---|---|
| `OPENAI_API_KEY` | 服务端统一 API Key |
| `OPENAI_BASE_URL` | 统一服务地址；默认可使用官方地址 |
| `OPENAI_MODEL` | 同时满足文本结构化输出与图片输入的模型 |
| `MODEL_MAX_CONCURRENCY` | 默认 `3` |
| `MODEL_TIMEOUT_SECONDS` | 默认 `90` |
| `MODEL_MAX_RETRIES` | 默认 `2`，即最多执行 3 次 |
| `OPENAI_AGENTS_DISABLE_TRACING` | 默认 `1` |
| `REVIEWER_NAME` | 本地人工复核显示名称 |
| `DATA_ROOT` | 默认 `./data` |
| `RETENTION_DAYS` | 默认留空，不自动删除 |

真实 `.env` 必须加入 `.gitignore`；仓库只提交无真实密钥的 `.env.example`。

模型、Base URL 和 API Key 均不由前端填写。模型名称和提示词版本必须随任务记录，但不得记录 API Key。

### 4.4 依赖锁定

编码阶段必须生成 Python 与前端锁文件。不得在方案中固定未经本机验证的具体补丁版本；首次实现时完成最小模型探针后再锁定依赖。

## 5. 总体架构

```text
Vue Web UI
    |
    | HTTP + SSE
    v
FastAPI API Layer
    |
    +-- SQLite Repository
    +-- Local File Repository
    +-- In-memory Event Bus
    +-- LocalTaskDispatcher (single active task)
            |
            v
        Fixed Workflow
            |
            +-- Material Validator
            +-- DOCX/PDF/Image Parsers
            +-- Common Rule Registry
            +-- Checklist Generator Agent
            +-- Evidence Matcher
            +-- Rule/Text/Vision Checkers
            +-- Independent Verifier Agent
            +-- Result Aggregator
            +-- Excel/JSON Reporter
```

### 5.1 架构原则

1. Workflow 决定阶段和调用顺序，LLM 不决定流程。
2. 规则优先；确定性结论不得被 LLM 覆盖。
3. LLM 只能基于传入的上传材料证据判断，不使用网络或外部知识作为证据。
4. 所有模型输出必须通过 Pydantic Schema 校验。
5. 每个结果必须引用系统提供的 `evidence_id`，模型不能自由编造位置。
6. 任务之间串行，单任务内部并行。
7. 所有可替换基础设施经接口隔离，避免未来替换队列或数据库时改动业务核心。

## 7. 任务状态机

### 7.1 状态定义

| 状态 | 含义 |
|---|---|
| `CREATED` | 任务记录已创建 |
| `VALIDATING` | 校验文件、MIME、大小和 JSON |
| `PARSING` | 解析 DOCX、PDF 和图片 |
| `GENERATING_CHECKLIST` | 合并通用规则与动态批注要求 |
| `AWAITING_CHECKLIST_CONFIRMATION` | 等待用户确认核对清单 |
| `QUEUED` | 已确认，等待正式核对执行槽 |
| `MATCHING_EVIDENCE` | 为核对项匹配候选证据 |
| `CHECKING` | 规则、文本及图片核对中 |
| `AGGREGATING` | 风险复核与结果汇总 |
| `COMPLETED` | 全部核对完成且无 `ERROR` |
| `COMPLETED_WITH_ERRORS` | 流程完成但存在核对项 `ERROR` |
| `FAILED` | 任务级阻断错误，无法继续 |
| `CANCELLED` | 用户取消 |
| `INTERRUPTED` | 后端重启导致活动任务中断 |

### 7.2 状态规则

- 只有 `AWAITING_CHECKLIST_CONFIRMATION` 可以接受核对项编辑与确认。
- 确认后生成不可变的 `checklist_version`，正式核对只使用该版本。
- 后端启动时，将数据库中遗留的活动状态统一改为 `INTERRUPTED`。
- `FAILED` 表示任务级失败；单项失败使用结果 `ERROR`，不能把整项任务误标为失败。
- `AWAITING_CHECKLIST_CONFIRMATION` 不占用执行槽。
- 一个任务活动阶段结束或暂停后，调度器才启动队列中的下一项工作。

## 8. 输入契约

### 8.1 上传要求

每个任务必须且只能包含：

- 1 个说明书 DOCX。
- 1 个模板 DOCX。
- 1 个项目 JSON。
- 0～N 个依据 PDF。
- 0～N 个依据图片。

同一 SHA-256 文件在同一任务中不得重复上传。MVP 默认单文件上限 50 MB、单任务总量上限 200 MB，均应可配置。

扩展名、声明 MIME 和文件签名字节必须一致；仅检查扩展名不合格。

### 8.2 项目 JSON Schema

```json
{
  "schema_version": "1.0",
  "project": {
    "product_name": "string | null",
    "model": "string | null",
    "brand": "string | null",
    "market": "string | null",
    "language": ["string"]
  },
  "attributes": {
    "任意业务字段": "string | number | boolean | string[] | null"
  }
}
```

规则：

- `schema_version` 必填，首版仅接受 `1.0`。
- `project` 与 `attributes` 必填。
- 核心字段可为空；某字段缺失时只影响引用它的核对项。
- `attributes` 只允许一层键值，不接受任意深度嵌套对象。
- 键名在内部执行 Unicode 规范化、空白清理和别名匹配，原始值同时保留。

## 9. 文档标准化模型

所有文档解析为统一的 `DocumentGraph`：

```text
DocumentGraph
├── document_id
├── source_file_id
├── kind: manual | template | evidence_pdf | evidence_image
├── blocks[]
│   ├── block_id
│   ├── block_type: heading | paragraph | table_cell | image | page_text
│   ├── text
│   ├── heading_path[]
│   ├── order_index
│   ├── locator
│   └── related_asset_ids[]
├── comments[]
├── assets[]
└── parse_warnings[]
```

### 9.1 DOCX 解析

必须直接解析 OOXML：

- `word/document.xml`：正文、表格、Drawing 和批注范围。
- `word/comments.xml`：批注内容与批注 ID。
- `word/_rels/document.xml.rels`：图片关系。
- `word/media/*`：图片资源。

必须用 `commentRangeStart`、`commentRangeEnd`、`commentReference` 和 comment ID 精确建立：

```text
批注 -> 被圈选文本/对象 -> 段落或表格单元格 -> 标题路径 -> 前后文 -> 邻近图片
```

不得依靠字符串搜索猜测批注位置。若 DOCX 使用编码实现暂不支持的批注形态，应产生解析告警并要求用户确认，不能静默忽略。

DOCX Locator 示例：

```json
{
  "heading_path": ["2 安全说明", "2.1 电池"],
  "block_type": "paragraph",
  "block_index": 12,
  "comment_id": "7",
  "quote": "请仅使用指定型号的电池"
}
```

DOCX 不承诺页码。`lastRenderedPageBreak` 只能作为调试信息，不作为报告中的可靠证据位置。

### 9.2 PDF 解析

- 按页提取文本块、表格近似结构、坐标和内嵌图片。
- 每页提取文字量低于可配置阈值且主要由整页图片构成时，判定为扫描型 PDF。
- 扫描型 PDF 在 MVP 中作为不支持的材料处理：如果是必需依据，则任务预检失败；如果是可选依据，则记录告警并忽略该文件。
- PDF Locator 必须包含页码和矩形坐标；报告至少展示页码和摘录。

### 9.3 图片处理

- 验证可解码性、尺寸、像素数量和颜色模式。
- 统一方向，处理 EXIF Orientation。
- 为模型输入生成受限尺寸的副本，保留原图哈希和来源。
- 不单独引入 OCR；图片文字由视觉模型在核对时读取。

## 10. 核对项生成

### 10.1 权威来源边界

- 模板批注：定义模板特有核对要求。
- 批注圈选的正文、表格或图片：作为批注上下文和定位锚点。
- 未批注模板正文：不得由 LLM 自由推导核对要求。
- 通用规则目录：定义不依赖单个模板批注的稳定核对要求。

### 10.2 通用规则目录

通用规则以版本控制内的 YAML 或 JSON 配置维护，每条规则至少包含：

| 字段 | 含义 |
|---|---|
| `rule_id` | 稳定唯一 ID |
| `version` | 规则版本 |
| `name` | 展示名称 |
| `description` | 核对要求 |
| `check_type` | 字段、结构、语义或图片 |
| `default_severity` | `CRITICAL` 或 `NORMAL` |
| `required_sources` | 需要的依据类型 |
| `applicability` | 适用条件 |
| `executor` | 对应确定性执行器或模型通道 |

首批规则至少覆盖产品名称、型号、品牌、目标市场、语言、必要章节以及可由项目 JSON 确定的字段。

### 10.3 动态批注核对项

Checklist Generator Agent 的输入只包含：

- 当前批注文本。
- 批注圈选内容。
- 标题路径、表格位置和有限前后文。
- 可用依据材料类型清单。
- 通用规则摘要，用于映射而非重复生成。

输出必须符合 `GeneratedCheckItem`：

```text
source_comment_id
name
requirement
check_type: FIELD | SEMANTIC | VISUAL | STRUCTURE
severity_suggestion: CRITICAL | NORMAL
severity_reason
required_source_categories[]
target_hint
rule_mapping_id | null
generation_warnings[]
```

规则：

- 一条批注包含多个独立要求时，应拆成多项，并共享 `source_comment_id`。
- 多条批注表达同一要求时只提出合并建议，不得在用户确认前静默删除。
- 找不到明确可执行要求时生成带告警的核对项，不得跳过批注。
- LLM 建议的 `CRITICAL` 必须引用批注中的触发语义；不能只输出主观判断。
- 动态项最终转换为 `CUSTOM_SEMANTIC`、`CUSTOM_VISUAL`、`CUSTOM_STRUCTURE` 或映射到既有通用规则。

### 10.4 关键项定义

只有以下来源可以产生关键项：

1. 通用规则的 `default_severity=CRITICAL`。
2. 批注明确包含法规、认证、安全、强制、禁止或不可缺失含义，LLM提出建议。
3. 用户在核对清单确认页手工设置。

用户确认后的严重等级才是本任务最终等级。无法确定时默认为 `NORMAL` 并显示等级告警。

### 10.5 强制确认节点

生成清单后任务进入 `AWAITING_CHECKLIST_CONFIRMATION`。页面必须支持：

- 查看来源批注及圈选内容。
- 查看或编辑核对项名称、要求、类型、严重等级和所需依据。
- 启用或停用核对项。
- 查看合并/拆分和缺失依据告警。
- 确认全部清单。

确认动作生成不可变的 `checklist_version` 和快照。后续修改必须重新生成版本并重新执行，不允许悄悄改变已执行清单。

## 11. 证据匹配

### 11.1 原则

- 先定位证据，再判断结论。
- 证据匹配模块只产生候选证据，不产生 PASS/FAIL。
- 模型只能引用候选集合中的 `evidence_id`。
- 未定位到证据必须明确记录，不能让模型凭常识补全。

### 11.2 无向量数据库检索方案

一期使用以下组合：

1. 字段别名、标准化值和精确匹配。
2. 标题路径、批注锚点和文档顺序邻近性。
3. 中文字符 n-gram 与英文 token 的 BM25/词频排名。
4. 表格行列标题匹配。
5. 图片与所在段落、标题和关系 ID 的结构关联。
6. 必要时由 LLM 只对有限候选摘要重新排序，不允许读取网络或自主搜索整个文件系统。

默认每个来源最多向核对模型提供 8 个文本候选块及必要的相邻块；具体上限可配置。若候选不足，返回 `MISSING_TARGET_CONTENT` 或 `MISSING_SOURCE_DATA`。

### 11.3 依据优先级与冲突

- 模板定义“检查什么”，不是事实依据。
- 说明书是被检查对象，不是自身正确性的依据。
- 项目 JSON、认证 PDF、ID 图和其他依据默认没有全局优先级。
- 模板核对要求明确指定依据类型时，优先使用指定材料。
- 多个依据对同一事实冲突时，结论必须为 `NEEDS_REVIEW`，原因码为 `SOURCE_CONFLICT`，并同时展示冲突证据。

## 12. 核对执行

### 12.1 执行通道

| 通道 | 适用内容 | 实现 |
|---|---|---|
| `FIELD_RULE` | 型号、名称、品牌等精确字段 | 确定性代码 |
| `STRUCTURE_RULE` | 必要标题、章节、表格/图片存在性 | 确定性代码 |
| `SEMANTIC_AGENT` | 语义一致性、复杂要求 | 无工具文本 Agent |
| `VISION_AGENT` | 图片文字、标识和视觉内容 | 无工具视觉 Agent |

确定性规则结论不可被 LLM 改写。如果规则无法执行，应返回明确错误或待复核原因，而不是自动转交模型猜测。

### 12.2 模型输出契约

所有判断 Agent 输出统一的 `AgentJudgement`：

```text
conclusion: PASS | FAIL | NEEDS_REVIEW
reason_code
reason
target_evidence_ids[]
source_evidence_ids[]
differences[]
missing_information[]
```

模型不得直接输出 `NOT_APPLICABLE` 或 `ERROR`：

- `NOT_APPLICABLE` 由适用性规则或用户确认产生。
- `ERROR` 由程序在解析、Schema 校验、超时或重试耗尽后产生。

结构化输出校验失败属于可重试错误；重试时使用相同证据快照，避免重试过程改变输入。

### 12.3 风险分级复核

- 通用确定性规则不做模型复核。
- 所有 `CRITICAL` 模型核对项执行第二次独立验证。
- `NORMAL` 项首次结论为 `FAIL` 时执行第二次独立验证。
- 第二次验证只接收要求和原始证据，不接收首次结论或理由。
- 两次结论一致时保留该结论，并保存两次运行记录。
- 两次结论不一致时输出 `NEEDS_REVIEW/MODEL_DISAGREEMENT`。

### 12.4 并发、超时和重试

- 任务之间串行排队。
- 单任务内相互独立的规则核对与模型核对并行。
- 模型调用通过全局 `asyncio.Semaphore` 限制，默认并发 3。
- 单次模型调用默认超时 90 秒。
- 对限流、临时网络错误和 5xx 最多重试 2 次，使用指数退避和随机抖动。
- 参数错误、认证错误和确定性内容错误不重试。
- 尊重服务端返回的限流等待信息。

### 12.5 模型隐私与追踪

- Agents SDK 远程 tracing 默认关闭。
- 如未来启用 tracing，必须禁用敏感输入/输出采集并单独评审。
- 应用日志只记录任务 ID、核对项 ID、模型名、耗时、Token 用量、重试次数和错误类型。
- 不记录 API Key、完整提示词、完整文档内容、图片 Base64 或完整模型响应。

## 13. 结果模型

### 13.1 核对项结论

| 结论 | 语义 |
|---|---|
| `PASS` | 证据充分且符合要求 |
| `FAIL` | 证据充分且明确不符合 |
| `NEEDS_REVIEW` | 材料不足、来源冲突、要求含糊或模型不一致 |
| `NOT_APPLICABLE` | 经适用性规则或用户确认不适用 |
| `ERROR` | 实际未完成核对的技术错误 |

禁止把超时、模型异常或解析异常包装成 `NEEDS_REVIEW`。

### 13.2 原因码最小集合

```text
MATCH
MISMATCH
MISSING_TARGET_CONTENT
MISSING_SOURCE_DATA
SOURCE_CONFLICT
AMBIGUOUS_REQUIREMENT
MODEL_DISAGREEMENT
NOT_APPLICABLE_BY_RULE
PARSER_ERROR
MODEL_TIMEOUT
MODEL_AUTH_ERROR
MODEL_RATE_LIMIT_EXHAUSTED
STRUCTURED_OUTPUT_ERROR
INTERNAL_ERROR
```

原因码用于筛选、统计和测试；面向用户的中文理由单独保存。

### 13.3 人工复核

- 用户可以修改任何系统结论。
- `system_conclusion` 永久保留，人工操作只更新 `final_conclusion`。
- 从 `FAIL`、`ERROR` 或 `NEEDS_REVIEW` 改为 `PASS` 时必须填写复核说明。
- 关键项发生任何改判时必须填写复核说明。
- 用户可以补充文字说明，但一期不能向已运行任务追加或替换原始材料。
- 材料错误时必须新建任务。
- 人工复核不会自动更新规则、提示词或未来任务行为。

## 15. API 契约

统一前缀：`/api/v1`。

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/tasks` | multipart 创建任务并上传完整材料 |
| `GET` | `/tasks` | 获取本地任务列表 |
| `GET` | `/tasks/{task_id}` | 获取任务状态、进度和摘要 |
| `GET` | `/tasks/{task_id}/events` | SSE 实时事件 |
| `GET` | `/tasks/{task_id}/check-items` | 获取待确认或已确认清单 |
| `PATCH` | `/tasks/{task_id}/check-items/{item_id}` | 编辑、启停或调整等级 |
| `POST` | `/tasks/{task_id}/check-items/confirm` | 确认清单并进入核对队列 |
| `GET` | `/tasks/{task_id}/results` | 分页、筛选核对结果 |
| `GET` | `/tasks/{task_id}/results/{result_id}` | 获取结果与证据详情 |
| `POST` | `/tasks/{task_id}/results/{result_id}/review` | 提交人工复核 |
| `POST` | `/tasks/{task_id}/retry-errors` | 只重试 `ERROR` 项 |
| `POST` | `/tasks/{task_id}/reports` | 生成 Excel 或 JSON 报告 |
| `GET` | `/tasks/{task_id}/reports/{report_id}` | 下载报告 |
| `POST` | `/tasks/{task_id}/cancel` | 取消排队或运行任务 |
| `DELETE` | `/tasks/{task_id}` | 删除任务及全部文件 |

要求：

- 所有错误返回统一结构：`code`、`message`、`details`、`request_id`。
- 所有更新操作校验任务状态。
- 清单编辑使用版本号进行乐观锁控制，避免页面重复提交覆盖。
- 文件下载只根据数据库记录解析，不接受任意磁盘路径参数。

### 15.1 SSE 事件

最小事件类型：

```text
task.stage_changed
task.progress_changed
task.awaiting_confirmation
task.completed
task.completed_with_errors
task.failed
task.cancelled
```

事件至少包含 `event_id`、`task_id`、`type`、`stage`、`progress`、`message` 和 `created_at`。断线重连后，页面先通过 `GET /tasks/{id}` 恢复最新状态，再重新订阅；一期不保证重放全部历史 SSE 事件。

## 16. 前端页面

### 16.1 任务列表

- 显示名称、创建时间、状态、阶段、进度和结果统计。
- 支持进入任务、删除任务。
- 不做用户归属和权限过滤。

### 16.2 新建任务

- 分区上传说明书、模板、项目 JSON、PDF 依据和图片依据。
- 创建前显示格式、大小和重复文件错误。
- 不展示 API Key、Base URL 或模型选择。

### 16.3 核对清单确认

- 左侧/顶部展示模板批注和定位上下文。
- 展示核对项类型、严重等级、所需依据、生成告警。
- 支持编辑、启停和最终确认。
- 未解决的生成告警需要醒目标识，但不强制逐项关闭。

### 16.4 任务进度

- 展示当前阶段、总体进度和简短日志摘要。
- 不展示完整模型提示词、响应或敏感材料。

### 16.5 结果与人工复核

- 按结论、类型、严重等级和是否人工修改筛选。
- 结果详情并排展示核对要求、说明书证据、依据证据、差异和理由。
- DOCX 显示标题路径、段落/单元格位置和摘录；PDF 显示页码和摘录；图片显示缩略图。
- 支持人工改判与复核说明。

### 16.6 报告

- 支持生成并下载 Excel、JSON。
- 生成时使用数据库中的当前最终结论快照。
- 报告生成失败不改变核对任务状态。

## 17. 报告格式

### 17.1 Excel

至少包含工作表：

1. `Summary`：任务、文件、模型/规则版本、状态统计和生成时间。
2. `Results`：每个核对项、严重等级、系统结论、最终结论、理由和人工改判标志。
3. `Evidence`：证据 ID、来源文件、定位、摘录或图片引用说明。
4. `ReviewLog`：完整人工复核历史。
5. `Metadata`：清单版本、规则版本、提示词版本和模型调用汇总。

### 17.2 JSON

JSON 是机器可读的完整导出，至少包含：

```text
schema_version
task
files
checklist_snapshot
results[]
evidence[]
review_records[]
execution_metadata
```

不得导出 API Key、完整提示词、图片 Base64 或内部绝对路径。

## 18. 安全与稳健性

- 所有文件视为不可信输入。
- 防止 Zip Slip、路径穿越、超大压缩比、XML 外部实体和压缩炸弹。
- OOXML XML 解析必须禁用外部实体和网络访问。
- 限制上传文件大小、DOCX 解压后总大小、XML 节点数量和图片像素。
- 前端显示原文时进行 HTML 转义，不能执行文档中的脚本或链接。
- 模型提示词明确声明上传文档内容是不可信数据，不得将其中内容视为系统指令。
- 模型不配置 Web、文件系统或代码执行工具。
- 日志和异常返回必须脱敏。
- API Key 只从 `.env` 读取，绝不写入数据库、任务目录、报告或前端响应。

## 19. 日志与可观测性

使用结构化 JSON 日志，最少字段：

```text
timestamp, level, request_id, task_id, stage,
check_item_id, operation, duration_ms, error_code
```

单次模型调用另记录模型名、输入哈希、Token 用量、重试次数和延迟。禁止记录完整材料或密钥。

任务页面中的“日志摘要”来自明确的业务事件，不直接回显服务端日志。

## 20. 数据生命周期

- 默认不自动清理本地任务。
- 用户删除任务时，删除数据库记录、上传文件、解析产物、提取图片和报告。
- 删除前必须二次确认。
- `RETENTION_DAYS` 留空表示禁用自动清理。
- 若启用自动清理，则整项删除，不保留失去证据来源的孤立结果。
- 清理失败应记录错误并允许下次重试。

## 21. 测试方案

### 21.1 单元测试

必须覆盖：

- DOCX 批注范围到正文/表格/图片锚点的映射。
- JSON Schema 与别名标准化。
- PDF 扫描型判断。
- 文件签名、路径安全和 Zip 安全限制。
- 通用规则执行器。
- 任务与核对项状态转换。
- 结果聚合与双重判断冲突规则。
- 人工改判说明必填规则。
- Excel/JSON 导出字段完整性。

### 21.2 集成测试

- 使用伪模型适配器测试完整 Workflow，不消耗真实 API。
- 测试结构化输出损坏、限流、超时、认证失败和重试耗尽。
- 测试 SSE 断线后通过任务查询恢复状态。
- 测试后端重启后活动任务标记为 `INTERRUPTED`。
- 测试删除任务时数据库和文件的一致性。

### 21.3 模型契约测试

真实 API 最少验证：

- 结构化输出能够被 Pydantic 解析。
- 配置模型支持图片输入。
- 超时与认证错误能被正确映射。
- 并发 3 路时限流处理符合预期。
- 第二次独立判断没有收到第一次结论。

### 21.4 端到端评估

对 5 组人工标注任务包执行：

1. 核对项召回率统计。
2. 结论准确率统计。
3. 证据引用有效性审计。
4. 三次重复运行稳定性测试。
5. 总耗时、模型耗时和 Token 用量统计。

若未达到第 2.3 节门槛，不得通过“修改验收数据”宣告完成；应定位问题属于解析、生成、证据匹配还是判断阶段。

## 22. 实施顺序与完成门槛

### 阶段 A：工程骨架

交付：前后端可启动、SQLite 迁移、配置加载、任务目录与健康检查。  
完成门槛：本机一条命令分别启动前后端，前端可访问健康接口。

### 阶段 B：输入与解析

交付：上传校验、项目 JSON、DOCX 批注解析、PDF/图片解析、统一 DocumentGraph。  
完成门槛：解析夹具测试全部通过；每条测试批注均能准确定位。

### 阶段 C：清单生成与确认

交付：通用规则注册表、Checklist Generator Agent、清单确认页面、版本快照。  
完成门槛：对测试模板生成完整清单，用户编辑与确认后不可变。

### 阶段 D：证据与核对

交付：证据检索、四类核对通道、风险分级复核、并发和重试。  
完成门槛：伪模型集成测试覆盖所有五类最终结果及主要原因码。

### 阶段 E：结果、复核与报告

交付：结果页、证据展示、人工复核、Excel/JSON 报告。  
完成门槛：系统结论与人工结论同时保留，导出结果与页面一致。

### 阶段 F：评估与收口

交付：5 组评估数据运行结果、指标报告、README 和已知限制。  
完成门槛：达到第 2.3 节全部指标；未达标项必须保留为明确问题，不得静默降级。

## 23. AI Coding 执行约束

后续交给 AI 编码时，应使用以下总指令：

1. 严格按本冻结方案实施，不自行扩大 MVP 范围。
2. 每次只完成一个实施阶段，并运行该阶段测试。
3. 不得用占位返回、硬编码演示结果或吞掉异常来伪造端到端成功。
4. 对缺少的样例或真实 API Key，应提供可运行的伪模型和夹具，但必须明确标注真实模型测试尚未完成。
5. 所有文件修改都应与当前阶段相关，不改动无关用户文件。
6. 完成每个阶段后报告：改动文件、测试命令、实际结果、未解决问题和下一阶段入口。
7. 若发现本文存在无法同时满足的要求，应停止相关实现，列出冲突和最小决策问题，不得擅自改变产品语义。

## 25. 变更控制

下列变化视为范围变更，必须先更新冻结方案再编码：

- 新增 DOC、扫描 PDF OCR 或其他输入格式。
- 取消核对清单人工确认。
- 允许 LLM 从未批注正文自由生成要求。
- 引入多用户、权限或生产部署。
- 改用 Celery/Redis/PostgreSQL 或对象存储。
- 允许模型使用外部搜索、工具或多 Agent 协作。
- 改变五类结论的语义。
- 改变依据冲突处理规则。
- 自动学习或自动发布通用规则。
- 修改验收门槛。

除上述范围变更外，编码执行者可以自行决定函数拆分、UI 微调、具体索引实现和非业务性的库内组织，但不得改变本文定义的输入、状态、结果、审计和证据语义。
