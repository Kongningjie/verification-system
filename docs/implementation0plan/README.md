# 说明书核对系统分阶段实施计划

本目录是后续 Coding 的执行入口。所有实现必须以 [冻结方案](./00_说明书核对系统_冻结方案.md) 为唯一产品与架构基线。

## 冻结基线

- 文件：`00_说明书核对系统_冻结方案.md`
- SHA-256：`B22EEEA0F7A1AE32CA93B99F459AB249FE65625A1AA70590613B237E0CA4A7F7`
- 状态：只读冻结
- 未经用户明确书面允许，不得修改、覆盖、移动、重命名或重新格式化冻结方案。
- 如果实现与冻结方案冲突，应停止 Coding，报告冲突并等待用户决策；不得通过修改冻结方案消除冲突。

每次开始 Coding 前应执行：

```powershell
(Get-FileHash -LiteralPath docs\implementation0plan\00_说明书核对系统_冻结方案.md -Algorithm SHA256).Hash
```

输出必须与上述 SHA-256 一致。若不一致，立即停止。

## 阶段划分

| 阶段 | 主题 | 核心产物 |
|---:|---|---|
| 1 | 材料接入与文档解析 | 上传、文件安全、项目 JSON、DOCX/PDF/图片解析、DocumentGraph |
| 2 | 核对清单生成与确认 | 通用规则、批注动态生成、清单编辑、版本快照、确认门禁 |
| 3 | 证据匹配与核对执行 | 候选证据、四类执行通道、Agents SDK、复核、并发与重试 |
| 4 | 结果闭环与报告 | 结果查询、证据详情、人工复核、Excel/JSON、主要前端页面 |
| 5 | 评估、稳健性与验收 | 五组基准任务、指标评估、安全审计、端到端收口 |

执行顺序固定为 `1 → 2 → 3 → 4 → 5`。不得并行跨阶段实现。

## 每次 Coding 的强制流程

每次 Coding 只能处理一个阶段，并按以下顺序执行：

1. 校验冻结方案哈希和 Git 工作区状态。
2. 阅读冻结方案、当前阶段计划及已有代码，不读取后续阶段作为本轮实现范围。
3. 明确本轮文件清单和测试清单。
4. 实现当前阶段，不顺手实现下一阶段功能。
5. 执行代码 Review：正确性、范围、数据安全、错误处理、可测试性和冻结方案一致性。
6. 修复 Review 中的阻断问题。
7. 运行当前阶段全部测试，并回归此前阶段测试。
8. 输出阶段报告，包括改动、Review 发现、测试命令与结果、已知限制。
9. 停止，不进入下一阶段。
10. 只有用户明确回复允许开始下一阶段，才能继续。

## 通用完成定义

一个阶段只有同时满足以下条件才算完成：

- 阶段范围内的功能真实可运行，不使用硬编码结果或吞异常伪造成功。
- 本阶段单元测试、集成测试和此前阶段回归测试全部通过。
- Ruff、前端类型检查和前端构建通过。
- 数据库迁移可从空库执行至最新版本，并可正确回退本阶段迁移。
- Review 无未处理的 P0/P1 问题。
- 未修改冻结方案，哈希保持不变。
- 未实现计划外功能。
- 阶段报告已提交给用户并等待下一步授权。

## Review 分级

- `P0`：数据泄露、文件越界、结论伪造、破坏原始材料、冻结方案被修改；必须立即停止。
- `P1`：核心流程错误、状态机不一致、证据不可追溯、错误被误报为业务结论；阶段不得完成。
- `P2`：非阻断的稳健性、可维护性或体验问题；应在本阶段修复或明确记录。
- `P3`：优化建议；可以进入后续待办，但不得借机扩展范围。

## Git 约束

- 只使用 `main` 分支。
- 每个阶段完成 Review 和测试后再形成阶段提交。
- 不得改写远程历史，不使用强制推送。
- 未获用户允许，不得因实现困难而回退或变更冻结方案。
